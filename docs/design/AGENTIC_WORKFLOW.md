# Agentic Workflow Architecture

How Astro's AI agents execute tasks: from plan graph to result delivery, including context flow, observability, and event streaming.

---

## 1. Overview

Astro automates software engineering by breaking projects into a **directed acyclic graph (DAG)** of tasks, each solved by an autonomous AI agent. The pipeline:

1. User creates a project with a vision document
2. AI generates a plan (DAG of tasks with dependencies)
3. Dispatch engine resolves ready tasks and assigns them to machines
4. Agent-runner executes each task in an isolated git worktree
5. The Claude SDK agent loop iterates: LLM generates → tools execute → results feed back
6. Events stream back via WebSocket relay → server persists to DB → frontend renders via SSE

Each task is self-contained: the agent receives a prompt (assembled from the vision doc, task description, and dependency outputs) and works autonomously until completion.

## 2. End-to-End Workflow

```
┌─────────┐     ┌──────────┐     ┌──────────────┐     ┌──────────────┐
│  User    │────▶│  Server  │────▶│   Dispatch    │────▶│ Agent-Runner │
│ (React)  │     │  (Hono)  │     │   Engine      │     │  (CLI/WS)    │
└─────────┘     └──────────┘     └──────────────┘     └──────────────┘
      ▲               │                                       │
      │               │              ┌────────────┐           │
      │               │◀─────────────│   Relay     │◀──────────┘
      │               │   (events)   │   Server    │  (WebSocket)
      │               │              └────────────┘
      │               ▼
      │         ┌──────────┐
      └─────────│   SSE    │
       (stream) │ Endpoint │
                └──────────┘
```

### Sequence

1. **Plan creation**: `POST /api/plan/generate` → AI generates nodes/edges → stored in `plan_nodes` / `plan_edges`
2. **Dispatch**: `DispatchEngine.tick()` finds nodes with all dependencies satisfied → creates `task_executions` → assigns to machines
3. **Execution**: Agent-runner receives assignment via WebSocket → sets up worktree → runs `TaskExecutor`
4. **Agent loop**: Claude SDK adapter iterates: send prompt → receive response → execute tools → send results → repeat
5. **Event streaming**: Each tool use, result, text chunk, and file change flows: agent-runner → WS → relay-server → persist to `streaming_events` → emit → SSE → frontend
6. **Completion**: Agent-runner sends `task:complete` → server updates `task_executions` → dispatch engine re-ticks

## 3. Plan Graph Structure

The plan is a DAG where:
- **Nodes** (`plan_nodes`): individual tasks with title, description, acceptance criteria
- **Edges** (`plan_edges`): dependency relationships (`source` must complete before `target` starts)
- **Milestones**: special nodes that bridge subgraphs (group related tasks)
- **Branches**: git branches, one per subgraph or milestone

### Disconnected Subgraphs

A plan may contain disconnected subgraphs (no edges between them). These execute independently and in parallel. Milestones can bridge subgraphs — when a milestone depends on nodes from multiple subgraphs, it creates a synchronization point.

**Current limitation**: No context flows between disconnected subgraphs. Each subgraph's tasks only see outputs from their direct DAG ancestors.

## 4. Context Flow & Information Propagation

### Per-Task Prompt Assembly

`ContextAssembler` (`server/lib/context-assembler.ts`) builds the execution prompt:

```
┌─────────────────────────────────────────┐
│              Execution Prompt            │
├─────────────────────────────────────────┤
│  System instructions                     │
│  ─────────────────────────────────────  │
│  Vision document (global, read-only)     │
│  ~4.5K tokens                            │
│  ─────────────────────────────────────  │
│  Task description + acceptance criteria  │
│  ─────────────────────────────────────  │
│  Dependency outputs (from DAG parents)   │
│  Up to ~2.5K tokens per dependency       │
│  (10K chars, truncated)                  │
│  ─────────────────────────────────────  │
│  Repository context (file tree, etc.)    │
└─────────────────────────────────────────┘
```

### Dependency Outputs

When task B depends on task A (via a DAG edge), B's prompt includes A's `markdown_summary` from `task_executions`. This is the primary mechanism for information propagation.

The summary is generated by the agent at task completion and stored in `task_executions.markdown_summary`. It's truncated to 10K characters in the prompt.

### What Flows Where

| Source | Scope | Mechanism |
|--------|-------|-----------|
| Vision document | All tasks | Included in every prompt via `ContextAssembler` |
| Dependency output | Direct DAG ancestors only | `dependencyOutputs` in prompt template |
| Repository state | All tasks on same branch | Git worktree reflects prior task commits |
| Session history | Same task only | Chat/steer messages stored in `sessions` |

### Knowledge Gaps

- **Cross-subgraph**: Tasks in disconnected subgraphs cannot see each other's outputs
- **Parallel siblings**: Tasks running in parallel (same depth, no edges) don't share context
- **Cross-milestone**: After a milestone merge, subsequent tasks only see the milestone's summary, not individual task outputs from before the milestone

## 5. Observability & Data Capture

### What Gets Stored

| Table | What | Granularity | Used For |
|-------|------|-------------|----------|
| `observation_events` | Full LLM prompts/responses | Per-turn (input/output JSONB) | Debugging, cost tracking |
| `task_executions` | Aggregated metrics, markdown_summary | Per-task | Dispatch, context propagation |
| `streaming_events` | Real-time event log | Per-event (text, tool_use, tool_result, file_change, session_init) | SSE catch-up, page refresh recovery |
| `sessions` | Conversation history | Per-chat/steer interaction | Chat continuity |

### Event Types in `streaming_events`

| Event Type | Source | Data |
|------------|--------|------|
| `text` | LLM text output | Buffered text chunks |
| `tool_use` | Agent calls a tool | `toolName`, `toolInput` |
| `tool_result` | Tool returns result | `toolName`, `result`, `success` |
| `file_change` | File created/modified/deleted | `path`, `action`, `linesAdded`, `linesRemoved` |
| `session_init` | Agent session starts | `sessionId`, `model` |

### Persistence Architecture

Events are persisted **globally in relay-server.ts** when they arrive via WebSocket, regardless of whether any SSE listener is connected. This ensures no events are lost during browser disconnects or page refreshes.

```
Agent-Runner ──WS──▶ Relay Server ──┬──▶ streamingEventLog.append() [DB]
                                    │
                                    └──▶ emit('task:*', msg)
                                              │
                                              ▼
                                    SSE handler (events.ts)
                                    └──▶ stream.writeSSE() [to browser]
```

The SSE handlers in `events.ts` use the DB sequence number (`_dbSeq`) from relay-server persistence as the SSE event ID, ensuring consistency with the catch-up endpoint (`GET /api/events/catch-up`).

## 6. Event Streaming Pipeline

### Flow

```
┌──────────────┐     ┌──────────────┐     ┌────────────────┐     ┌─────────┐
│ Agent-Runner │────▶│  WebSocket   │────▶│  Relay Server  │────▶│   SSE   │
│ (Claude SDK) │     │  Client      │     │  (persistence  │     │ (events │
│              │     │              │     │   + emit)      │     │  .ts)   │
└──────────────┘     └──────────────┘     └────────────────┘     └─────────┘
                                                │                      │
                                                ▼                      ▼
                                          streaming_events       Browser
                                          (Postgres)             (React)
```

### Recovery Layers

Three layers ensure event delivery survives disconnections:

1. **Live SSE**: Real-time streaming via `events.ts` SSE endpoint
2. **Streaming events DB**: `streamingEventLog` persists all events globally in relay-server.ts. On SSE reconnect, `Last-Event-ID` header triggers catch-up from DB
3. **Observation fallback**: `GET /api/events/catch-up` endpoint reads from `streaming_events` table for full task history

### Error Handling

- **WebSocket disconnect**: Messages are lost if WS is not OPEN (agent-runner buffering is a future improvement)
- **Persistence failure**: Each handler wraps `streamingEventLog.append()` in try-catch. Persistence errors are logged but don't prevent event emission to SSE listeners
- **SSE disconnect**: Browser reconnects with `Last-Event-ID`, catches up from DB

## 7. Context Window Budget

### Token Estimates

| Component | Approximate Tokens |
|-----------|-------------------|
| System instructions | ~1K |
| Vision document | ~4.5K |
| Task description + criteria | ~0.5-2K |
| Per-dependency output | Up to ~2.5K (10K chars) |
| Repository context | ~1-3K |
| **Total (N dependencies)** | **~7K + 2.5K × N** |

With Claude's 200K context window, this leaves substantial room for the agent's multi-turn conversation. A task with 5 dependencies uses ~20K tokens for the initial prompt, leaving ~180K for the agent loop.

### Recommendations

- Add a total prompt size guard in `buildExecutionPrompt()` to warn when approaching limits
- Consider summarizing dependency outputs more aggressively for tasks with many ancestors
- Future: token budget allocation when project-level knowledge store is added

## 8. Parallel Execution & Resource Model

### How Parallelism Works

- Dispatch engine identifies all tasks with satisfied dependencies
- Multiple tasks can execute concurrently on the same machine
- Each task runs in an **isolated git worktree** (separate working directory, shared git objects)
- Agent-runner manages multiple `TaskExecutor` instances

### Resource Considerations

- **Git worktrees**: Lightweight (shared `.git`), but file I/O can contend on slow disks
- **LLM API calls**: Each task makes independent API calls; rate limits apply globally
- **Memory**: Each task executor holds its conversation history in memory
- **Logging**: Per-task log lines include `taskId` prefix for filtering
