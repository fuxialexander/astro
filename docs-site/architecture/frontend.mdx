## Overview

The Astro frontend is a Vite 7 + React 19 single-page application written in strict TypeScript. All routing is client-side via React Router v7. State is managed by 29 Zustand stores that persist via the `dataClient` abstraction to `/api/data/*` endpoints backed by Drizzle ORM.

There is **no mode branching** in frontend code. The same React components, stores, and hooks run identically in local mode (PGlite) and server mode (Supabase). Mode differences are handled entirely in the backend.

### Store Pattern

Every store follows the same structure:

```typescript
import { create } from 'zustand'
import { dataClient } from '@/lib/data-client'

interface ProjectStore {
  projects: Project[]
  loading: boolean
  error: string | null
  load: () => Promise<void>
  addProject: (p: Partial<Project>) => Promise<Project>
}

export const useProjectStore = create<ProjectStore>((set) => ({
  projects: [],
  loading: false,
  error: null,

  load: async () => {
    set({ loading: true, error: null })
    try {
      const projects = await dataClient.listProjects()
      set({ projects, loading: false })
    } catch (err) {
      set({ error: err instanceof Error ? err.message : 'Failed to load', loading: false })
    }
  },

  addProject: async (partial) => {
    const project = await dataClient.createProject(partial)
    set((s) => ({ projects: [...s.projects, project] }))
    return project
  },
}))

// Always use selectors — never subscribe to the whole store
const project = useProjectStore((s) => s.projects.find(p => p.id === projectId))
```

### Two-Phase Data Loading

`DataLoader` (in `src/app.tsx`) orchestrates startup loading in two phases:

```
Phase 1 — Teams
  Sets X-Team-Id header used by all subsequent API calls

Phase 2a — Critical stores (block render until done)
  usePlanStore.load()        GET /api/data/plan?slim=1
  useProjectStore.load()     GET /api/data/projects
  useExecutionStore.load()   GET /api/data/executions?slim=1
  useUserProfileStore.load() GET /api/data/profile
  useSidebarStore.load()     GET /api/data/sidebar

Phase 2b — Non-critical stores (load in background)
  useSettingsStore, useUsageStore, useSessionStore,
  useInitiativeStore, useActivityStore, usePluginStore,
  useSkillStore, useGithubStore, ...
```

The **slim load** (`?slim=1`) excludes large fields (`content`, `executionOutput`, `streamText`) to keep initial transfer at 1–5 MB instead of 50+ MB. Per-project full loads happen on navigation via `useProjectData()`.

## Plan Graph Visualization

The plan graph uses `@xyflow/react` (React Flow). The plan is a directed acyclic graph of `PlanNode`s connected by `PlanEdge`s.

### Edge Types

| Type | Meaning |
|------|---------|
| `dependency` | Target depends on source; source must complete first |
| `branch` | Target is an alternative exploration path from source |

### Node Implementation Pattern

```typescript
import { type Node, type NodeProps } from '@xyflow/react'

// 1. Define typed node data
type TaskNodeData = Node<{
  task: PlanNode
  isSelected: boolean
  onDispatch: () => void
}>

// 2. Implement node component
function TaskNode({ data }: NodeProps<TaskNodeData>) {
  const { task } = data
  return (
    <div className={cn('rounded-lg border p-3', statusColors[task.status])}>
      <p className="font-medium">{task.title}</p>
      <StatusBadge status={task.status} />
    </div>
  )
}

// 3. Cast nodeTypes to avoid React Flow type issues
const nodeTypes = { task: TaskNode } as any

// 4. Always wrap in ReactFlowProvider when using useReactFlow()
export function PlanGraphView() {
  return (
    <ReactFlowProvider>
      <PlanGraph nodeTypes={nodeTypes} />
    </ReactFlowProvider>
  )
}
```

## SSE Streaming

### Typed Parsers

Use the typed wrappers from `@/lib/sse-parser` — never parse raw SSE manually:

```typescript
import { parseChatSSE, parseExecutionSSE } from '@/lib/sse-parser'

// Chat / plan generation streaming
const response = await fetch('/api/chat', {
  method: 'POST',
  body: JSON.stringify({ projectId, message }),
})
for await (const event of parseChatSSE(response)) {
  switch (event.type) {
    case 'text': appendText(event.text); break
    case 'plan_result': applyGeneratedPlan(event.plan); break
    case 'tool_use': showToolCall(event); break
    case 'done': break
  }
}

// Task execution streaming
const response = await fetch(`/api/stream/${executionId}`)
for await (const event of parseExecutionSSE(response)) {
  switch (event.type) {
    case 'text': appendOutput(event.text); break
    case 'tool_use': showToolCall(event); break
    case 'file_change': showFileChange(event); break
    case 'result': handleResult(event.result); break
    case 'done': markComplete(); break
  }
}
```

### Execution Event Types

| Event | Description |
|-------|-------------|
| `init` | Execution started |
| `session_init` | Agent session initialized; includes model name |
| `text` | Agent text output |
| `tool_use` | Agent tool call (name + input JSON) |
| `tool_result` | Tool call result |
| `file_change` | File modified, created, or deleted |
| `progress` | Progress percentage (0–100) |
| `result` | Final result with status and `UsageMetrics` |
| `error` | Execution error with message |
| `aborted` | Execution cancelled by user |
| `heartbeat` | Keep-alive ping |
| `done` | Stream complete |

### Page-Refresh Recovery

```typescript
// src/hooks/use-restored-execution.ts
const { events, isRestored } = useRestoredExecution(executionId)
```

On page refresh, `useRestoredExecution` fetches `streaming_events` from the DB via `fetchStreamingEventsCatchUp()` and replays them — identical UI to live streaming. For active executions, it reconnects to the SSE stream and fetches any missed events by sequence number.

## Activity Rendering

Activity events are rendered via the centralized system in `activity-blocks.tsx`.

```typescript
import {
  groupActivityEvents,
  TextBlock,
  ToolBlock,
  ToolGroupBlock,
  FileChangeBlock,
} from '@/components/activity/activity-blocks'

// Group raw events into display blocks
const blocks = groupActivityEvents(events)

// Render each block
{blocks.map((block) => {
  switch (block.type) {
    case 'text':       return <TextBlock key={block.id} block={block} />
    case 'tool':       return <ToolBlock key={block.id} block={block} />
    case 'tool_group': return <ToolGroupBlock key={block.id} block={block} />
    case 'file_change':return <FileChangeBlock key={block.id} block={block} />
  }
})}
```

### `TaskActivityEvent` Union Type

```typescript
type TaskActivityEvent =
  | TextEvent
  | ToolUseEvent
  | ToolResultEvent
  | FileChangeEvent
  | SteerEvent
  | ErrorEvent
  | ChatUserEvent
  | ChatAssistantEvent
  | ApprovalRequestEvent
  | ApprovalResponseEvent
  | MutationEvent
```

## Feature Flags

```typescript
import { useFeatureFlag } from '@/hooks/use-feature-flag'

function MyFeature() {
  const enabled = useFeatureFlag('my-feature')
  if (!enabled) return null
  return <MyFeatureUI />
}
```

`GLOBAL_DEFAULTS` in `use-feature-flag.ts` must have identical keys and values to the backend's `feature-flags.ts`.

For route-level gating:

```typescript

  <MyFeaturePage />
</FeatureFlagRoute>
```
